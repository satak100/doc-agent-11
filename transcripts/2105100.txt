### 3. Compare conventional OCR, TrOCR, PaddleOCR-VL and another published method.

A reasonable four-method comparison is Tesseract, TrOCR, PaddleOCR-VL 1.6 and Donut.

Tesseract is the conventional OCR baseline. It is useful because it gives a low-complexity reference for how traditional OCR behaves before domain adaptation.

TrOCR is an end-to-end Transformer OCR model using a visual Transformer encoder and text Transformer decoder. The published method explicitly supports fine-tuning on human-labelled recognition data.

PaddleOCR-VL is closer to modern multimodal document parsing than traditional line OCR. The current Paddle documentation identifies PaddleOCR-VL-1.6 as the latest model in that series, and the 1.6 work describes an enhanced compact document-parsing model. Your project reproduces/adapts the pretrained `PaddlePaddle/PaddleOCR-VL-1.6` checkpoint without weight updates.

Donut is an OCR-free document-understanding Transformer. That makes it an interesting architectural comparison, but it is not an ideal apples-to-apples CER baseline because its intended task includes document understanding rather than only transcription.

There are two meanings of “fair baseline.” **Tesseract is a fair conventional baseline.** However, if the question is whether TrOCR fine-tuning helps, the strongest causal baseline is the **same frozen TrOCR checkpoint before fine-tuning**. Comparing frozen TrOCR against fine-tuned TrOCR changes one important variable rather than changing the entire architecture.

The current project has measured PaddleOCR-VL evidence, but no measured Tesseract-versus-TrOCR experiment in this ZIP. That distinction should remain explicit.

### 4. Define a leakage-safe train/validation/heldout split.

The course specification itself warns to split by document, not by individual page when pages from the same scan/document can cross splits.

For this corpus I would first create grouping IDs before assigning a split. Each group should include exact duplicates, resized/recompressed copies, duplicate Drive objects and perceptually near-identical images. Because the provenance records 25 duplicate-name pairs preserved using Drive-ID suffixes, filename identity alone is not a safe grouping rule.

A defensible future training split would be something like 70% train, 15% validation and 15% heldout **by group**, not raw image count. The exact percentage is less important than the grouping.

The current 12 held-out pages should remain untouched. They should not be used to choose enhancement settings, crop rules, retry thresholds, epochs or prompts after looking at their measured scores. If the current experiments were repeatedly chosen based on those same 12 pages, they function partly as a development set rather than a truly untouched final test set.

For template leakage, I would also record a template-family ID. Exact or near-identical template scans must stay in one split. A separate template-generalization evaluation can intentionally hold out an entire template family.

The current `Page.id` implementation hashes the **relative filename**, not image content. Therefore two identical images under different filenames receive different IDs. Content/perceptual deduplication must happen outside that ID mechanism.

### 5. Explain CER, WER, medication entity F1, retrieval recall@k and groundedness.

**CER** is character edit distance divided by reference characters. It catches spelling/digit mistakes well. It can mislead because a low global CER can be dominated by easy text while the medically important drug string is wrong.

**WER** performs edit distance at word level. It is intuitive but harsh about tokenization. One spacing error can turn an almost-correct phrase into several word errors.

**Medication-entity precision** asks what fraction of predicted medication entities were accepted as correct. **Recall** asks what fraction of labelled medications were recovered. **F1** combines them.

There is an important project-specific caveat: `scripts/evaluate_ocr.py` calls its metric “fuzzy entity F1” and counts a medication pair as matching at normalized Levenshtein similarity `>= 0.75`. That can be useful for measuring approximate OCR, but in a medical system it can also classify a sufficiently similar **wrong drug or wrong strength** as a true positive. Therefore this F1 must not be described as clinical medication correctness.

**Retrieval recall@k** measures whether a relevant result appears anywhere in the first `k` retrieved chunks. Your five-query evaluation gives recall@5 = 1.00 for E5, hashing and hybrid. But five queries are a very small set, and recall@5 can hide poor rank ordering. A system can score 1.00 while the useful result frequently appears at rank 5 rather than rank 1.

Your current retrieval labels are also mostly exact Latin-script medicine-name queries. That does not yet demonstrate the claimed benefit for real Bangla paraphrases.

**Groundedness** asks whether answer claims are supported by retrieved evidence. It can also mislead: an answer may faithfully quote **incorrect OCR** and therefore be textually grounded but clinically wrong. Groundedness is not equivalent to medical correctness.

### 7. Design and critique raw-page, enhancement, selective-retry and Rx-crop experiments.

The experiments should share exactly the same held-out pages and scoring code.

**Raw page** is the control. It preserves all information but gives the model large amounts of irrelevant header, stamp and template content.

**Classical enhancement** in this repository uses EXIF correction, autocontrast with 1% cutoff, a 3×3 median filter and sharpness factor 1.35. Before looking at results, I would predict that it could improve strong printed text but damage faint or thin handwriting by modifying subtle strokes.

**Selective retry** keeps the main OCR path and reruns generations that hit the token ceiling with a larger 1,536-token cap. The repository also removes obvious repetitive autoregressive tails. This may recover truncated content, but it increases compute and can also generate more wrong text.

**Rx crop** uses the OCR spotting result to find the Rx anchor when possible and crops away content above/left of that region. This should increase the effective resolution and attention devoted to medicine lines. Its risk is cutting away relevant page context or relying on a wrong Rx anchor.

The most important methodological rule is that the crop/retry choice cannot be made using the true label for each page at test time.

### 11. Review the ingest → layout → OCR → chunk → embedding → index contracts.

I found several concrete failure cases.

`Page.id` is derived from the relative path rather than image content, so duplicate images with different filenames are not automatically identified.

`Region` has page ID, bounding box and kind, but the main OCR implementation does not actually crop and transcribe each region. `vision/ocr.py` retrieves cached **whole-page OCR once per page** and ignores the region bounding boxes. The store verifies one vector per chunk but does not persist the full OCR/preprocessing/chunk configuration alongside the index. A stale index could therefore survive a changed OCR or chunk configuration unless scripts/directories are managed carefully.

### 12. Why did 64/16 beat 128/24 and 256/32 for E5?

The measured chunk ablation is:

64/16: 943 chunks; E5 recall@5 = 1.00.
128/24: 505 chunks; E5 recall@5 = 0.80.
256/32: 328 chunks; E5 recall@5 = 0.20.

Hash and hybrid recall remained 1.00 at all three sizes.

The likely reason is that prescription evidence is locally concentrated. A short query such as a drug name benefits from a chunk where that drug and its immediate dose/context occupy a large fraction of the representation. With a 256-word chunk, several medicines, header text and instructions can be blended into one dense vector, reducing the salience of one rare exact medication string.

The 16-word overlap also protects short medication evidence near chunk boundaries.

But this is only five labelled retrieval queries, so the evidence supports: **“64/16 performed best on our current five-query E5 ablation.”** It does not support the universal claim that 64/16 is best for E5.

### 13. Compare multilingual E5, signed feature hashing and hybrid RRF.

Multilingual E5 provides the semantic component and is the natural candidate for Bangla/English paraphrases because the model family was trained on multilingual text pairs.

The project's signed feature hashing is a lexical representation. In this implementation it hashes normalized **word-like tokens**, not character n-grams. That makes it useful for exact strings such as medicine names, but less robust than character n-grams would be to OCR misspellings or internal character corruption.

Hybrid RRF combines **rank positions** rather than trying to calibrate E5 cosine scores against hashing scores. That is a sensible design when the two systems produce fundamentally different score distributions.

The current five-query result is 1.00 recall@5 for all three systems, so the measured data does **not yet prove that hybrid is superior**. It only shows that hybrid retained the successes of both on this small set.

Also, the current queries are mostly exact English medication queries such as `Phoscon 210mg`, `Fixcef Plus 500mg` and `Rupadim 10mg`. To justify the claim about Bangla paraphrases, add labelled Bangla natural-language queries whose relevant evidence does not contain the same surface tokens.

### 15. Review the privacy redactor against PII recall ≥0.98.

The regex audit initially looks strong: raw OCR contains hundreds of detector-visible email/name/phone occurrences, while the final indexed chunks have zero unresolved matches for those **same detector patterns**.

But that is not recall, because a detector cannot measure identifiers that it never recognized.

The manually labelled pilot gives the more honest result:

12 pages
12 visually present patient-name entities
1 explicitly detected and redacted
2 OCR-extracted names leaked into the index
9 patient names omitted by OCR.

Therefore:

explicit detection/redaction recall = 1/12 = **0.0833**

conditional redaction recall when OCR extracted the name = 1/3 = **0.3333**

end-to-end non-disclosure = 10/12 = **0.8333**

The target PII entity recall ≥0.98 therefore **fails**.

OCR omission should not be counted as successful PII detection. It happens to prevent text-index disclosure, but it demonstrates nothing about redactor quality.

The current detector only handles email, Bangladesh-format phones and English lines matching `Name:`. It can miss Bangla name labels, clipped labels, OCR-corrupted `Name`, addresses, registration IDs and other identifier types.

A proper final privacy holdout should independently annotate patient names, phones, emails, patient/registration IDs, full addresses and other in-scope identifiers. It should preferably use two reviewers/adjudication, score each type separately, and score both detector-only recall on gold text and end-to-end image→index leakage.

Most urgently, public GitHub publication of the identifiable heldout images must be resolved because regex redaction of indexed text does not anonymize the raw JPEGs.

### 17. Optimize the RTX 4090 run without changing evaluation.

Your GPU runner already implements most of the right ideas.

It sorts images by dimensions so similar shapes are batched together. It uses batching, `torch.inference_mode()`, BF16 model weights, PyTorch SDPA attention, left padding, cache-enabled deterministic generation, resumable JSONL outputs, selective retry only for capped generations, and recursive OOM fallback that splits the batch without changing the sample.

That preserves evaluation better than reducing image resolution or output length after an OOM.

Additional discipline:

keep the same dtype/model/decoding settings across compared variants;

cache the raw OCR because chunk and retrieval ablations do not need to rerun vision;

cache embeddings when only the index/search implementation changes;

record which samples used OOM fallback;

do not choose retry/crop based on heldout gold errors;

preserve sample IDs after size sorting so evaluation order cannot be mixed up.

I also found a reproducibility contradiction: `reports/a2_readiness.md`/`build_index.sh` refer to a tested environment using much newer Transformers/PyTorch for the PaddleOCR-VL 1.6 runner, but `pyproject.toml` and `requirements.lock` pin `torch==2.3.1` and `transformers==4.44.2`. ### What remains uncertain

The largest unresolved issue is the fine-tuning requirement. A1 proposed TrOCR fine-tuning and the course specification describes fine-tuning a pretrained OCR model, but the measured A2 reader is pretrained PaddleOCR-VL 1.6 without weight updates. Either an honest fine-tuning experiment needs to be run using additional aligned transcription labels or the team needs instructor clarification.

Privacy also remains unresolved because the 12-page pilot covers patient names only and fails the target. More PII entity types and independent annotation are required.

OCR quality remains too weak for clinical interpretation. Even the best measured crop result has entity F1 around 0.505.

There is also a data-governance uncertainty that must be resolved before public submission: identifiable heldout prescription images are present while raw data is described as restricted.
