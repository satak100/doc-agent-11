2. Why this corpus is hard

Handwriting is difficult because character shapes vary by writer, pen pressure, spacing, abbreviation and stroke connection. Medication names are particularly unforgiving: changing even one or two characters can turn one drug string into another.

Bangla/English code-switching makes recognition and retrieval harder because one prescription can contain Bengali script, Latin drug names, English abbreviations, digits and Bengali numerals. A recognizer or tokenizer that is strong on one script can still fail at transitions between scripts.

Repeated printed templates help layout because headers occur in predictable areas, but they also compete with handwriting for OCR attention or token budget. The evidence shows at least one page where whole-page OCR produced only the header while a crop recovered medication lines.

Shadows, perspective, JPEG artifacts and uneven illumination alter stroke contrast. However, your experiment does not justify the broad statement that “enhancement is bad.” It only shows that the particular classical enhancement recipe tested reduced medication-entity F1 from 0.490 to 0.413 on the 12-page sample.

3. Pipeline and Page → Region → Chunk contract

The fixed contracts are very small:
- `Page`: `id`, `image_path`, `doc_id`.
- `Region`: `page_id`, bounding box, and `kind` such as heading/text/table/figure.
- `Chunk`: `id`, `doc_id`, `text`, one or more `page_ids`, plus retrieval `score`.

The intended conceptual flow is Page → layout Regions → OCR text → redaction/normalization → text Chunks → embeddings → index.

But there is an implementation nuance you should not hide in a viva: the current cached OCR adapter effectively emits one page-level text chunk per page and does not attach the OCR line polygons to the `Region` objects. `layout.detect()` makes only a heading region and a body region using a fixed height ratio. So “typed Page→Region→Chunk contracts” is true at the interface level, but the final cached OCR path does not fully exploit fine-grained region-to-text associations.

4. Why PaddleOCR-VL 1.6 is adapted pretrained OCR, not fine-tuning

You load an existing pretrained PaddleOCR-VL model and change inference conditions around it: BF16/SDPA, batching, token cap, retry policy, crop strategy and tail trimming. Those are adaptation/inference/preprocessing choices.

Fine-tuning would require updating model weights using labelled prescription examples and an optimizer. The repository contains no evidence of such weight updates. Therefore “pretrained, adapted; not fine-tuned” is the honest description.

5. CER, WER and medication-entity F1

Your evaluation covers 12 pages and 61 reference medication-name/strength entries.

CER measures character-level edit error. Lower is better. Baseline CER is 0.499; crop+trim is 0.413. CER is sensitive to spelling-level corruption.

WER measures word-level edit error. Lower is better. Baseline and crop+trim are both about 0.702. One wrong character can make an entire word count as wrong, so WER can remain high even if some character-level errors improve.

Medication-entity F1 asks a different question: did the system recover the medication-name/strength entities? It balances precision and recall. Baseline F1 is 0.490; crop+trim is 0.505. In the crop+trim run, precision is about 0.587 and recall about 0.443, corresponding to 27 true positives, 19 false positives and 34 false negatives.

The metrics therefore measure different failure modes. A text can have a somewhat better CER but still miss clinically important medicine entities.

6. Why crop+trim improves metrics but is still unsafe clinically

Crop+trim reduces irrelevant header content and gives the OCR model more effective capacity for the Rx body. On the measured set, CER improves from 0.499 to 0.413 and entity F1 from 0.490 to 0.505.

But F1 ≈ 0.505 and recall ≈ 0.443 are far too weak for autonomous medication decisions. The failed-page example still contains errors such as corrupted strengths and names after crop recovery. Therefore the safe claim is: crop+trim is a better recovery aid for search/review, not a clinically trustworthy transcription system.

Also, saying the crop experiment “proves layout/token-budget competition was the cause” is too strong. The result is consistent with that explanation, but cropping changes several things at once, including image area and effective sequence burden. It supports the hypothesis; it does not isolate causality.

7. Why 64/16 was selected

The chunk ablation used five retrieval queries at k=5:
- 64 words / 16 overlap: E5 recall@5 = 1.00.
- 128 / 24: E5 recall@5 = 0.80.
- 256 / 32: E5 recall@5 = 0.20.

Hybrid recall@5 remained 1.00 for all three settings, and mean hybrid latency stayed around 2.7 ms. Therefore 64/16 is the best measured choice for dense E5 retrieval on this tiny evaluation set.

Why it can help: smaller chunks dilute a medication mention with less unrelated prescription text while 16-word overlap reduces the chance of splitting a medication from nearby strength/schedule context.

But five queries are too few to claim 64/16 is universally optimal. You can say it was selected by the available ablation.

8. Why E5, feature hashing and RRF complement one another

`intfloat/multilingual-e5-small` gives a 384-dimensional semantic representation and is useful for multilingual or paraphrased queries.

Signed lexical feature hashing gives a 2048-dimensional sparse-style lexical signal. It is useful when exact strings such as drug names and strengths matter.

Reciprocal-rank fusion combines ranks rather than raw similarity scores, so you do not need to calibrate E5 cosine scores against lexical cosine scores.

Conceptually this is a sensible complement: semantic matching + exact lexical matching + rank-level fusion.

However, your current five-query evaluation does not empirically prove hybrid is superior, because E5, hashing and hybrid all achieve recall@5 = 1.00. The complementarity is a design rationale; superiority would need a larger, harder query set containing paraphrases, OCR corruptions and exact-name confounders.

11. Privacy pilot arithmetic

There are 12 visually present patient-name entities across 12 pages.

One was explicitly detected and redacted. So explicit detection/redaction recall is 1/12 = 0.0833.

OCR extracted only three of the 12 names into text: one was redacted and two leaked. Conditional on OCR extraction, the redactor caught 1 of 3, so conditional recall is 1/3 = 0.3333.

For end-to-end non-disclosure, one explicit redaction plus nine OCR omissions means 10 of the 12 names did not appear in the index. Therefore non-disclosure = 10/12 = 0.8333; leak rate = 2/12 = 0.1667.

Critical distinction: the nine OCR omissions reduce disclosure, but they are not successful redaction. A privacy detector cannot claim credit for identifiers it never saw.

12. Why zero regex matches did not prove privacy recall

The regex audit only asks whether known detector patterns remain after redaction. The patient-name rule is essentially an English line beginning with `Name:`; phone and email rules are also pattern-limited.

If OCR corrupts a name label, crops it, emits Bangla instead of the expected English label, or omits the name entirely, the regex can see nothing and still report zero unresolved matches. That is why the zero-match index scan is a leakage regression test, not a recall experiment.

Privacy recall requires independent ground-truth labels created from the images and then checking whether every labelled PII entity is removed from the indexed output.
